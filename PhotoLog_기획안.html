01

프로젝트 개요 및 목표

PhotoLog는 출사지 공유와 EXIF 기반 사진·장비 분석을 결합한 사진 커뮤니티입니다. KDT 풀스택 과정을 수료한 직후 시작하는 1인 개인 프로젝트로, CRUD·인증·페이징 같은 기본기를 확실히 다지는 것과, EXIF·기상·지도·AI API를 엮은 특화 기능으로 포트폴리오 차별성을 만드는 것, 두 목표를 동시에 가져갑니다.

개발 원칙은 하나입니다 — 코드는 본인이 한 줄씩 직접 작성하고, AI는 코드를 대신 짜주지 않고 리뷰와 개념 설명, 막힌 부분에 대한 조언 역할만 맡습니다. 유일한 예외는 Spring Security + JWT로, 이미 뼈대가 짜여진 코드를 그대로 쓰는 대신 함께 한 줄씩 뜯어보며 왜 이렇게 구성했는지 이해하는 데 집중합니다.

02

기술 스택

Frontend
React (TypeScript), Redux Toolkit, Axios, Vanilla CSS / CSS Modules, exifr(EXIF 파싱), SunCalc(월령 계산)
Backend
JDK 21, Spring Boot 3.x, Spring Security (JWT — 기존 스켈레톤 코드 리딩 기반 학습)
Persistence
MyBatis, MariaDB
AI Engine
Python 3.10+, FastAPI, LangChain, ChromaDB(RAG) · Ollama 로컬 오픈소스 LLM 서빙(1순위) 또는 Groq 무료 API(대안) — 자체 파인튜닝·vLLM은 스트레치 골
API / Tooling
Kakao Map API, OpenWeatherMap, TossPayments(결제 데모, 스트레치), Postman, Swagger UI
왜 바꿨나 — Unsloth 파인튜닝과 vLLM 서빙은 GPU 확보, 도메인 QA 데이터셋 구축, 학습·검증 사이클까지 변수가 많아 1인 개발 일정 안에 완결을 보장하기 어렵습니다. Ollama/Groq + RAG 조합은 "독립된 AI 백엔드 구축, RAG 파이프라인 설계, 도메인 특화 프롬프트 엔지니어링"이라는 원래의 스토리를 그대로 유지하면서 인프라 리스크만 제거합니다.
03

시스템 아키텍처

배포 없이 로컬에서 5개 서비스를 개별 실행하는 구조입니다. 프론트엔드는 항상 Spring Boot만 호출하고, AI 관련 요청일 때만 Spring Boot가 FastAPI에 위임합니다.

EXIF 파싱은 서버를 왕복하지 않고 프론트엔드에서 exifr로 즉시 처리합니다. 사진을 올리는 순간 카메라·렌즈·F값·셔터스피드·ISO·GPS를 화면에 바로 채워 보여주고, 사용자가 확인하거나(필름 카메라라면) 직접 수정한 뒤 "게시" 시점에 확정된 메타데이터를 이미지와 함께 Spring Boot로 전송합니다. Spring은 파싱 없이 저장만 담당하되, 값의 범위(F값·ISO 등)는 최소한으로 검증합니다.

파일 저장 정책

업로드 이미지(프로필 사진, 게시글 첨부, 갤러리 사진)는 클라우드 스토리지 없이 Spring 프로젝트의 upload 폴더에 저장하고, DB에는 파일 경로만 저장합니다. upload 폴더는 .gitignore로 제외합니다. 폴더 생성 로직(@PostConstruct)이 앱 구동 시 폴더가 없으면 자동으로 만들어주므로, 클론 직후에도 .gitkeep 없이 업로드가 정상 동작합니다.

패키지 구조 원칙

백엔드는 기능 단위로 패키지를 나누는 방식(package-by-feature)을 따릅니다. com.backend.member처럼 기능별 패키지 안에 controller·domain·dto·mapper·service를 함께 두고, 여러 기능이 공유하는 것(페이징 DTO, 파일 업로드 유틸, 스프링 설정)은 com.backend.global에, 인증/인가 인프라(필터·핸들러·JWT 유틸)는 com.backend.security에 모읍니다. 이후 게시판·갤러리 등 새 기능도 같은 컨벤션(com.backend.board, com.backend.gallery)을 따릅니다.

개발 순서 원칙

5개 핵심 기능을 동시에 벌리지 않고 순서대로 하나씩 구현합니다. 각 기능은 먼저 화면-API-DB가 끝까지 연결되는 최소 동작 버전(뼈대)을 완성해 파이프라인이 도는 걸 확인한 뒤, 예외 처리·유효성 검증·UX 디테일을 단계적으로 채워나갑니다.

05

핵심 기능 명세

① 회원 및 인증 MVP

페이지 — 로그인, 회원가입(아이디·비밀번호·닉네임 + 아이디 중복확인 + 프로필 사진 1장, 멀티파트 업로드), 마이페이지(닉네임·프로필 사진 수정, 회원탈퇴).

JWT 기반 인증(BCrypt 암호화, Access/Refresh Token)은 기존 스켈레톤 코드를 한 줄씩 리딩하며 원리를 이해하는 데 집중합니다. 회원탈퇴는 소프트 삭제로 처리해, 탈퇴 후에도 해당 회원이 남긴 게시글·사진은 유지하되 작성자 표시를 "탈퇴한 회원" 등으로 대체합니다.

스트레치 — 이메일 인증, 소셜 로그인, 관리자 페이지에서의 회원관리.

② 자유게시판 MVP

페이지 — 리스트(페이징), 상세, 등록(다중 이미지 업로드), 수정(삭제 기능 포함).

댓글·대댓글은 2단계로 제한합니다(대댓글에는 답글 불가). 다중 이미지 업로드는 우선 기본적인 <input type="file" multiple>로 동작을 먼저 완성하고, MyBatis <selectKey> + <foreach>로 board_image 테이블에 일괄 INSERT합니다. 게시글 삭제 시 연관된 이미지 파일과 댓글도 함께 정리되도록 설계합니다(DB ON DELETE CASCADE 또는 애플리케이션 레벨 처리).

스트레치 — 카테고리 필터, 드래그 앤 드롭 · 클립보드 붙여넣기 업로드.

③ 사진 갤러리 MVP

페이지 — 무한스크롤 그리드 리스트, 모달(exifr로 프론트에서 파싱한 EXIF 메타데이터 패널 + Kakao Map 좌표 레이어), 등록(다중 업로드 + 필름 카메라용 수동 입력 UI), 수정/삭제.

EXIF는 업로드 즉시 프론트에서 추출해 미리보기로 보여주고, 사용자가 확인·수정한 값을 게시 시점에 서버로 전송해 저장합니다.

스트레치 — TossPayments 결제 연동 데모. 모달에 "구매하기" 버튼을 추가해 결제위젯(테스트 카드) → 서버 승인 API → 성공/실패 페이지로 이어지는 최소 결제 흐름을 구현하고, 마이페이지 안에 결제 목록(구매 내역) 확인 페이지를 둡니다. 실제 마켓플레이스가 아니라 결제 연동 자체를 보여주는 데모가 목적이라 판매자 정산이나 실물 배송 로직은 다루지 않습니다.

④ 야간 출사지도 MVP

날짜 선택 — 오늘부터 5일 이내로 제한합니다(OpenWeatherMap 무료 티어의 예보 제공 범위).

대표 지역 — 서울, 강원(평창), 경기(가평), 충청(태안), 전북(무주), 전남(고흥 나로도), 경북(영양), 경남(거창), 제주 9곳의 좌표를 코드에 고정해두고 시작하며, 이후 실제 유명 출사지 위주로 목록을 보강합니다. 각 지역의 구름량·강수확률은 OpenWeatherMap에서, 월령·월광도는 SunCalc에서, 광해도는 지역별 정적 근사 테이블에서 가져와 Kakao Map 위에 마커로 표시합니다.

임의 지점 조회 — 지도를 클릭하면 그 좌표를 기준으로 동일한 정보를 모달로 보여줍니다. 구름량·강수확률은 클릭 좌표로 바로 조회하고, 광해도는 가장 가까운 대표 지역의 값을 근사치로 사용합니다.

종합 점수 — 구름량·강수확률·월광도·광해도 네 항목을 모달에 개별로 나열하는 동시에, 아래 가중합으로 하나의 추천 점수를 계산해 함께 보여줍니다.

score = 100 − (구름량×0.45 + 강수확률×0.20 + 월광도×0.20 + 광해도환산×0.15)
90+ 최적 70–89 좋음 50–69 보통 <50 비추천

스트레치 — 기상청 공공데이터 API로 전환, 더 세분화된 실시간 광해도 데이터, 대표 지역 확장.

⑤ AI 융합 서비스 MVP

FastAPI + LangChain + ChromaDB(RAG) 위에서 Ollama(로컬) 또는 Groq(무료 API)로 서빙하는 세 가지 기능을 제공합니다.

AI 촬영 피드백

사진의 EXIF(F값·셔터스피드·ISO·카메라)를 분석해 전문가 시점의 촬영 피드백을 생성합니다.

맞춤형 출사 가이드

야간 출사지도에서 조회한 날씨·월광도 데이터와 사용자 장비 정보를 조합해 조리개·셔터스피드·ISO 등 노출 세팅을 추천합니다 — ④번 기능과 실제로 데이터를 주고받는 지점입니다.

사진 · 장비 Q&A 챗봇

촬영 지식 문서를 ChromaDB에 임베딩해두고, 자유 질문에 RAG 기반으로 답변합니다.

스트레치 — 자체 파인튜닝(Unsloth QLoRA) 및 vLLM 서빙 도전, 유사 사진 추천(임베딩 기반 유사도 검색), 사진 자동 캡션·태그 생성(비전 모델).

시연 및 결과물 전략

상시 클라우드 배포는 하지 않습니다. Spring Boot + MariaDB + FastAPI + Ollama까지 무료로 상시 운영하기엔 비용·인프라 부담이 크고, 지금 단계에서는 우선순위가 아니기 때문입니다. 대신 GitHub 레포에 스크린샷, 아키텍처 다이어그램, 핵심 기술 의사결정 기록을 담은 README와 데모 영상(GIF)을 준비하고, 면접에서 필요하면 로컬에서 직접 라이브로 시연합니다.

08

로컬 개발 환경 운용 원칙

React, Spring Boot, FastAPI, Ollama, MariaDB 5개 서비스를 처음에는 Docker 없이 각각 손으로 기동합니다. 편의 도구보다 각 서비스가 어떤 명령어로 뜨고 어떻게 통신하는지 몸에 익히는 것을 우선하기 위한 선택이며, Docker(볼륨 마운트 + 핫리로드 기반 개발용 구성)는 기본기가 손에 익은 뒤 스트레치 골로 도입합니다.

09

트러블슈팅 및 학습 전략

  • 1차 자력 해결 — 에러 로그와 공식 문서(Spring, React, LangChain 등)를 기반으로 직접 구글링하여 해결 시도.
  • AI(Claude) 활용 원칙 — 코드는 직접 작성하고, Claude에게는 방향성 질문·코드 리뷰(보안, 쿼리 최적화, 타입 정의)·개념 설명을 요청.
  • Security+JWT 학습 — 기존 스켈레톤 코드를 한 줄씩 함께 리딩하며 각 구성 요소의 역할을 질문 기반으로 이해.
